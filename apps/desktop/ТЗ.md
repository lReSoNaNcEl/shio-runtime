# ТЗ: десктопный VTuber-ассистент «Фрирен» (Electron + TypeScript + Three.js)

> Документ — техническое задание для реализации с нуля. Исполнитель: модель Sonnet 4.6.
> Проект создаётся в `D:\Web\vtuber-app`. API-сервис — уже готовый локальный проект
> `D:\Web\python-speech` (ASR + TTS), он запускается отдельно.

---

## 1. Цель и суть

Десктопное приложение, отображающее 3D VTuber-модель (`.vrm`) и ведущее с ней голосовой/текстовый
диалог в образе персонажа **Холо** (волчица-мудрец). Цикл взаимодействия:

```
Пользователь (голос или текст)
   │  голос → ASR (python-speech /recognize)
   ▼
Текст пользователя
   │  → LLM (GroqCloud, llama-3.1-8b-instant) с системным промтом Холо
   ▼
Ответ LLM (текст)
   │  → TTS (python-speech /synthesize, engine=f5, voice=Alice)
   ▼
WAV-аудио ответа
   │  → воспроизведение + анализ амплитуды
   ▼
Анимация рта VRM через висемы (lip-sync) синхронно со звуком
```

**Важно:** в `python-speech` НЕТ LLM — он отдаёт только ASR и TTS. Всю оркестрацию
(ASR → Groq → TTS) выполняет само Electron-приложение.

MVP-приоритеты: рабочий полный цикл голос/текст → ответ Холо голосом + движение рта. Качество
артикуляции — упрощённое (по амплитуде). Без БД (история диалога — в памяти), но с абстракциями
под лёгкую замену LLM-провайдера и хранилища.

## 2. Технологический стек

- **Electron** (desktop shell), **TypeScript** (строгий режим).
- **Three.js** + **@pixiv/three-vrm** (загрузка и анимация VRM 0.x/1.0), `@pixiv/three-vrm-animation`
  (опц. для idle-анимаций).
- Сборка: **electron-vite** (Vite под main/preload/renderer, нативный TS, HMR).
- LLM: **GroqCloud** через OpenAI-совместимый REST (`groq-sdk` или `fetch`).
- Аудио: **Web Audio API** (захват микрофона + воспроизведение + `AnalyserNode` для lip-sync).
- HTTP к python-speech: из **main-процесса** (Node `fetch`/`undici`), чтобы обойти CORS и не
  светить ключи в renderer.

---

## 3. Архитектура Electron (безопасность обязательна)

Три слоя, общение через IPC:

- **main** (Node): окно, конфиг, ключ Groq, все сетевые вызовы (Groq + python-speech), память
  диалога, выбор `.vrm` через нативный диалог. Ключ Groq и любые секреты — ТОЛЬКО здесь.
- **preload**: `contextBridge` пробрасывает в renderer узкий безопасный API
  (например `window.api.recognize(wavBuf)`, `window.api.ask(text)`, `window.api.synthesize(text)`,
  `window.api.onSpeak(cb)`).
- **renderer** (TS + Three.js): 3D-сцена, VRM, lip-sync, захват микрофона (Web Audio),
  воспроизведение аудио, UI чата. БЕЗ доступа к сети/секретам напрямую.

Настройки безопасности окна: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`,
preload-скрипт. Микрофон в Electron работает в renderer через `navigator.mediaDevices.getUserMedia`.

**Почему сеть в main:** renderer (`file://`/`app://`) при прямых запросах к `http://localhost:8000`
упрётся в CORS, а ключ Groq нельзя держать в renderer. Поэтому: renderer захватывает аудио и играет
звук, а HTTP к python-speech и Groq идёт через main по IPC.

## 4. Поток данных (детально)

1. Пользователь жмёт «микрофон» (toggle/push-to-talk) **или** вводит текст в чат.
2. **Голос:** renderer захватывает PCM, ресемплит в 16 кГц моно, собирает **WAV** (см. §5.1),
   ArrayBuffer → IPC `asr:recognize` → main → `POST /recognize` → текст пользователя.
   **Текст:** строка идёт сразу как текст пользователя.
3. main: добавляет user-сообщение в `MemoryStore` → `LLMProvider.chat([system, ...history, user])`
   → Groq → текст ответа Холо → добавляет в `MemoryStore`.
4. main: `POST /synthesize { text: ответ, engine:"f5", language:"ru", voice:"Alice", speed:1.0 }`
   → байты WAV (+ заголовки метрик).
5. main → IPC `tts:speak` → renderer передаёт `{ text, audio: ArrayBuffer }`.
6. renderer: показывает реплику Холо в чате; `AudioPlayer` играет WAV; `LipSync` по амплитуде из
   `AnalyserNode` двигает висемы VRM; по окончании — рот закрывается.

Состояния UI на каждом шаге: `idle → listening → recognizing → thinking → speaking → idle`.

## 5. Интеграция с python-speech (контракт API)

**База:** `http://localhost:8000` (настраивается, `PYTHON_SPEECH_URL`). Сервис запускается отдельно:
`cd D:\Web\python-speech && .\scripts\simple_run.ps1`. Перед работой приложение проверяет
`GET /health` — у движков `engines.f5.mode == "real"`.

Эндпоинты (проверено по `/openapi.json`):

| Метод | Путь | Запрос | Ответ |
|---|---|---|---|
| GET | `/health` | — | `{status, asr:{status}, engines:{xtts:{status,mode}, f5:{status,mode}}}` |
| GET | `/voices` | — | `{default:"Alice", presets:[{key,label,emotions:[...]}], all_emotions:[...]}` |
| POST | `/recognize` | `multipart/form-data`, поле `file` = WAV (16 кГц, моно, PCM16) | `{text, segments:[{text,start,end,duration}], language, language_probability}` |
| POST | `/synthesize` | JSON (см. ниже) | **байты WAV** (`audio/wav`) + заголовки `X-Engine, X-Language, X-Emotion, X-Latency-Ms, X-RTF, X-Duration-Sec` |
| POST | `/synthesize/ab` | JSON | `{text, language, emotion, results:[{engine,audio_b64,latency_ms,rtf,duration_sec}]}` (для приложения не нужно) |
| WS | `/ws` | бинарные int16 PCM 16 кГц кадры; `{"type":"flush"}` для финализации | JSON-сегменты `{type:"segment", text, ...}` (опц., см. §5.2) |

**`SynthesizeRequest` (JSON для `/synthesize`):**
```jsonc
{
  "text": "строка",
  "language": "ru",          // "ru" | "en"
  "emotion": "neutral",      // опц.; у Alice есть neutral/happy/angry, прочее → fallback neutral
  "voice": "Alice",          // опц.; дефолт берётся из /voices
  "speed": 1.0,
  "pitch": 0.0,
  "engine": "f5"             // использовать "f5" (быстрый, RTF ~0.3; xtts — запасной)
}
```
Ответ — это **бинарный WAV**, читать как `arrayBuffer()`, НЕ как JSON.

### 5.1. Захват аудио для ASR — критичный нюанс
**НЕ использовать `MediaRecorder`** (он даёт webm/opus, который python-speech не декодирует → 500).
Захват только сырого PCM через Web Audio API: `AudioContext` → `getUserMedia` →
`ScriptProcessorNode` (или `AudioWorklet`) → собрать Float32 → ресемпл до 16 кГц → int16 →
сформировать корректный **WAV-контейнер на стороне клиента** → отправить в `/recognize`.
(Эталонная реализация уже есть в `D:\Web\python-speech\web\index.html` — переиспользовать логику
`downsample`/`encodeWav`/`floatToInt16`.)

### 5.2. Потоковый ASR (опционально, Phase 2)
Для «живого» распознавания по ходу речи — WebSocket `/ws`: слать int16 PCM 16 кГц кадры, получать
сегменты. Для MVP достаточно `/recognize` по кнопке (записал → отпустил → распознал).

## 6. Интеграция с GroqCloud (LLM)

- Endpoint (OpenAI-совместимый): `https://api.groq.com/openai/v1/chat/completions`.
- Модель: **`llama-3.1-8b-instant`** (вынести в конфиг `GROQ_MODEL`).
- Заголовок: `Authorization: Bearer ${GROQ_API_KEY}`.
- Тело: `{ model, messages, temperature: ~0.8, max_tokens: ~256, stream: false }`, где `messages` =
  `[{role:"system", content: SYSTEM_PROMPT}, ...история, {role:"user", content: текст}]`.
- Можно использовать пакет `groq-sdk` либо `fetch`. Вызов — только из main.
- **Ключ** хранится в `.env` (main, `process.env.GROQ_API_KEY`) или в settings-файле приложения;
  НИКОГДА не в renderer и не в репозитории. В UI настроек — поле для ввода ключа (сохранять в
  пользовательский config, напр. через `electron-store` или JSON в `app.getPath('userData')`).

### 6.1. Системный промт (вставить дословно)
```
Ты — Холо, Великий Волк-Дух Пшеницы, мудрая богиня с 400-летним стажем. Твой образ — девушка с волчьими ушами и хвостом.

Стиль общения:
1. Отвечай саркастично, язвительно и с юмором. Подкалывай собеседника, используй снисходительные обороты («Ох, люди...», «Прямо как ребёнок», «Ты серьёзно?»).
2. Отвечай кратко — максимум 2-3 предложения, если не требуется развёрнутое объяснение. Никакой воды.
3. Всегда давай полезный и точный совет или решение. Сарказм — это обёртка, а внутри — мудрость.
4. Обращайся к собеседнику как «путник», «малыш» или «глупый торговец». Иногда упоминай пшеницу, луну или старые времена.

Жёсткие правила:
- Если вопрос глупый — сначала высмей, потом ответь.
- Если вопрос сложный — ответь чётко, но с хитринкой.
- Никогда не будь по-настоящему злой или грубой. Ты добрая, но ворчливая.
```

## 7. Абстракции для расширяемости (требование заказчика)

Заложить интерфейсы, чтобы при смене Groq на другой сервис и при подключении БД менялась только
реализация, без переписывания логики.

```ts
// LLM-провайдер — заменяемый
interface ChatMessage { role: 'system'|'user'|'assistant'; content: string; }
interface LLMProvider {
  chat(messages: ChatMessage[]): Promise<string>;        // MVP: без стрима
  // chatStream?(messages): AsyncIterable<string>;        // Phase 2
}
class GroqProvider implements LLMProvider { /* fetch к Groq */ }

// Хранилище диалога/памяти — заменяемое (сейчас память, потом любая БД)
interface MemoryStore {
  getHistory(sessionId: string): Promise<ChatMessage[]>;
  append(sessionId: string, msg: ChatMessage): Promise<void>;
  clear(sessionId: string): Promise<void>;
}
class InMemoryStore implements MemoryStore { /* Map в памяти, обрезка истории по N сообщений */ }
// Позже: SqliteStore (better-sqlite3) / любой адаптер — без изменения остального кода.
```

Выбор реализаций — через конфиг/фабрику (`createLLMProvider(config)`, `createMemoryStore(config)`).
История ограничивается «окном» (например последние 10–20 сообщений) + системный промт всегда первым.

## 8. VRM-модель и сцена (Three.js + three-vrm)

- Загрузка `.vrm`: нативный диалог выбора файла (main, `dialog.showOpenDialog`, фильтр `*.vrm`),
  путь → renderer → `GLTFLoader` с `VRMLoaderPlugin` (`@pixiv/three-vrm`). Поддержать VRM 0.x и 1.0
  (three-vrm нормализует выражения).
- Сцена: перспективная камера по пояс/в рост, мягкий свет (ambient + directional), фон —
  однотонный/прозрачный, плавный `requestAnimationFrame`-цикл, `VRM.update(delta)` каждый кадр.
- Idle-жизнь: периодическое моргание (выражение `blink`), лёгкое покачивание/дыхание, опц.
  поворот головы к камере (LookAt). Это делает модель «живой» вне речи.
- Если `.vrm` не выбран — показать заглушку/подсказку «загрузите модель».

## 9. Lip-sync по амплитуде (выбранный подход для MVP)

При воспроизведении TTS-аудио:
- `AudioContext` → источник (`AudioBufferSourceNode` из полученного WAV) → `AnalyserNode` → выход.
- Каждый кадр: из `AnalyserNode` берём текущую громкость (RMS по `getByteTimeDomainData` или
  энергию по `getByteFrequencyData`), сглаживаем (low-pass/`lerp`).
- Маппинг громкости в висемы VRM через `vrm.expressionManager`: основная — открытие рта
  (выражение **`aa`**, вес = `clamp(volume * gain, 0..1)`). Для оживления — лёгкая подмешка/чередование
  `ih/ou/ee/oh` по полосам частот или псевдослучайно, чтобы рот не выглядел одной гласной.
- Тишина/конец аудио → все веса висем → 0 (плавно), рот закрыт.

Имена выражений: VRM 1.0 — `aa, ih, ou, ee, oh`; VRM 0.x — `A, I, U, E, O` (three-vrm даёт
унифицированный доступ через preset-имена). Вынести коэффициенты (gain, сглаживание, порог) в
константы для подбора.

> Upgrade-путь (не для MVP): точные висемы по фонемам (rhubarb-lip-sync по аудио, либо
> forced alignment). Архитектуру `LipSync` сделать так, чтобы источник «вес висемы по времени» можно
> было заменить с амплитудного на фонемный, не трогая VRM-слой.

## 14. Этапы (milestones)

1. **Каркас:** electron-vite + TS + безопасное окно; рендер Three.js-сцены; загрузка `.vrm` через
   диалог; idle + моргание.
2. **Текстовый цикл:** `pythonSpeechClient.health()`; `MemoryStore` + `GroqProvider`; ввод текста →
   ответ Холо в чате (без звука).
3. **TTS:** `POST /synthesize` (f5) → воспроизведение WAV в renderer (без lip-sync).
4. **Lip-sync:** `AnalyserNode` → висемы VRM синхронно со звуком; закрытие рта по окончании.
5. **Голос:** захват микрофона (PCM→WAV) → `/recognize` → текст → полный голосовой цикл.
6. **Настройки и полировка:** выбор `.vrm`, ключ Groq, URL, язык/голос; обработка ошибок; статусы.

(Phase 2, по желанию: стриминг Groq по предложениям + последовательный TTS для меньшей задержки;
WebSocket `/ws` для live-ASR; эмоция TTS из тональности ответа; БД-хранилище через `MemoryStore`.)

## 15. Критерии приёмки (проверка end-to-end)

Предусловие: `python-speech` запущен, `GET /health` → `engines.f5.mode == "real"`; задан `GROQ_API_KEY`.

1. Запуск приложения → выбор `.vrm` → модель отрисована, моргает, ведёт себя «живо».
2. Ввод текста (например «Сколько будет 2+2?») → Холо отвечает **по-русски, саркастично, в образе**,
   коротко (2-3 предложения) → голос проигрывается → **рот двигается синхронно** со звуком, по
   окончании закрывается.
3. Голос: нажать микрофон, произнести фразу → она распознаётся и появляется в чате как реплика
   пользователя → тот же цикл ответа голосом.
4. python-speech выключен → понятная ошибка, приложение не падает.
5. Замена провайдера/хранилища: показать, что добавление новой реализации `LLMProvider` /
   `MemoryStore` не требует правок в оркестраторе/UI (описать в README).

## 16. Известные подводные камни (учесть обязательно)

- **ASR-формат:** только WAV 16 кГц моно PCM; `MediaRecorder`/webm/opus → 500. Делать WAV вручную
  (эталон в `python-speech/web/index.html`).
- **TTS-ответ бинарный:** `/synthesize` отдаёт WAV-байты + `X-*`-заголовки, не JSON.
- **CORS/секреты:** сетевые вызовы к python-speech и Groq — из main-процесса, не из renderer.
- **Готовность сервиса:** проверять `/health` и `engines.f5.mode`; первый запуск python-speech качает
  модели (Whisper/XTTS/F5) и грузит ~10-20 c.
- **Эмоции голоса:** у голоса `Alice` фактически есть `neutral/happy/angry`; остальные → fallback
  neutral. Для MVP можно слать `neutral`; опц. — простая привязка эмоции к тональности ответа.
- **Микрофон в Electron:** требует разрешения `getUserMedia` в renderer; на Windows — системные
  настройки приватности микрофона.
- **VRM-версии:** поддержать 0.x и 1.0 (имена висем различаются; three-vrm унифицирует).
- **Длинный ответ:** Холо по промту отвечает коротко, но на всякий случай — резать длинный текст на
  предложения и синтезировать/проигрывать последовательно.
