# UX-аудит Shio Desktop App и направление редизайна

Дата: 11 июля 2026. Область: текущий Electron renderer и связанные UI-точки. Код продукта в рамках аудита не менялся.

## 1. Current UX Summary

Сейчас Shio воспринимается как development/debug shell, а не как законченный desktop-продукт: при старте весь экран занимает WebGL-canvas, сохранённая VRM загружается автоматически, а чат выглядит наложенной снизу панелью. В верхней панели смешаны название, агрегированный статус и два технических входа. Пользователь не получает ответа на главный вопрос: «что делать сейчас?».

Это подтверждается реализацией: `App` всегда монтирует canvas, а `Controller.attachCanvas()` сразу создаёт `SceneManager`, запускает RAF-цикл, проверяет health и при `cfg.vrmPath` вызывает `loadVrmFromPath()`. Overlay — отдельное Electron-окно, синхронизируемое через IPC; его жизненный цикл уже отделён от главного окна, хотя оба renderer сейчас используют общий стартовый путь.

## 2. Current Information Architecture

```text
Главное окно (одна сцена, без маршрутов)
├─ Canvas / VRM (full-screen, всегда смонтирован)
├─ TopBar: Shio · «ASR / TTS OK» · Отладка · Настройки
└─ ChatOverlay (правый нижний, сворачиваемый)
   ├─ сообщения
   ├─ статус диалога / прогресс речи
   └─ текстовый и голосовой ввод

Модальные диалоги
├─ Settings: Системные | Персонаж | LLM | Оверлей
└─ AvatarDebugDialog: технические вкладки и тесты Runtime

Отдельное окно Electron
└─ Overlay: собственный canvas; получает avatar state и mouth weights по IPC
```

Фактические поля Settings: ASR/TTS URL, язык/голос, микрофон; LLM-провайдер, ключ, модель и backlog selector; VRM, gaze и passive companion; overlay. Контролы continuous listening существуют в компоненте, но скрыты условием `false`, поэтому пользовательская IA и фактическая конфигурация расходятся.

### Visual, interaction и accessibility

* Сейчас много одинаковых тёмных прямоугольников, слабая page-title/subtitle и недостаточно различимы продуктовые и технические действия.
* Нативные `button` в tablist не имеют `role="tab"`, `aria-selected` и keyboard-модели стрелок; перед заменой нужны явный focus ring, предсказуемый tab order и Escape для всех диалогов.
* Enter отправляет текст без отдельного режима многострочного ввода; это допустимо для однострочного чата, но action должен быть явно видим.
* Нельзя подтверждать destructive действие Enter по умолчанию. Информация не должна отличаться только цветом; минимум кликабельной области — 40×40 px.

## 4. Proposed Information Architecture

```text
Shio
├─ Home                     краткий статус, quick actions, последняя активность
├─ Chat                     основной разговор и история текущей сессии
├─ Streamer                 continuous listening / режим внимания / overlay shortcut
├─ Avatar Preview           normal preview, камера, модель, текущая анимация
├─ Runtime Health           состояния сервисов и действия восстановления
├─ Settings                 General · Speech · LLM · Character · Avatar · Overlay · Advanced
└─ Debug (utility)          диагностика Runtime, тесты, timelines
```

History остаётся частью Chat до появления отдельного полноценного сценария поиска/архива. Полный Avatar Preview и Debug скрыты до запроса. Overlay конфигурируется в Settings → Overlay, а его открытие доступно из Home/Streamer и Avatar Preview. Header показывает только активный раздел, один health chip и Settings; при проблеме chip становится warning badge. В Desktop-окне лучше применить sidebar shell, а не top navigation: разделов уже больше шести, названия неоднородны, а окно имеет стартовый размер 1200×800.

## 5. Three UX Variants

|---|---|---|---|

| Startup | Chat, quiet status, recent activity, quick actions | Home с health, listening, overlay, последним диалогом | Chat + компактный live portrait, без debug controls |

| Риски | недооценивает режим стриминга | dashboard может стать панелью индикаторов без задачи | маленький VRM всё равно требует lifecycle и дизайн-проработку |
| Сложность / миграция | низкая–средняя / низкая | средняя / средняя | средняя–высокая / средняя–высокая |

## 6. Recommended Direction

Выбрать **A — Chat-first**, с небольшой Home-сводкой как вторым разделом, а не как обязательным стартом. Реальный основной пользовательский цикл уже реализован вокруг текстового и голосового диалога; VRM и огромный `AvatarDebugDialog` сегодня в значительной мере служат проверке embodiment. Поэтому это решение делает готовый сценарий главным, не выдавая текущий инструмент разработки за пользовательский экран.

Это не запрещает C в будущем: после отделения preview можно проверить, нужен ли компактный portrait на Chat/Home. Не следует делать его частью первой миграции: это снова свяжет readiness чата с WebGL и создаст риск неявно изменить Avatar Runtime.

### Startup flow

```text
Запуск → shell + Sidebar + Chat доступны сразу
       → health проверяется независимо и тихо обновляет chip
       → Chat работает; незаполненная конфигурация показывает actionable empty state
       → VRM не читается, SceneManager/RAF не создаются в main window
       → пользователь открывает Avatar Preview → создаётся canvas → VRM грузится → idle стартует
```

`main app Avatar Preview` и `overlay Avatar Runtime` должны оставаться разными потребителями представления. Закрытие preview должно останавливать только его renderer/loop и не должно закрывать overlay. Перед реализацией нужно зафиксировать контракт: overlay продолжает поднимать свой renderer при открытии и получает state/mouth updates только в рамках уже существующего IPC-канала. Auto-idle при открытом Preview сохраняется; при закрытом Preview не должен становиться скрытым обязательным background-rendering требованием.

## 7. Settings Recommendation

Перейти на **левую вертикальную навигацию**, не копируя Discord: это навигация внутри desktop-настройки, а не список сообществ. В ширине ≥ 760 px: левый rail 184–208 px, правая область 560–720 px, фиксированные nav и footer, scroll только у content. При < 760 px заменить rail на `Picker`/compact section button в шапке; при < 560 px открыть Settings как full-height view, а не сжимать сложную форму.

Рекомендуемые группы на основе существующих полей:

* **General** — поведение приложения и история.
* **Speech** — ASR/TTS URL, язык, голос, микрофон.
* **Listening** — continuous listening и attention mode; убрать скрытие существующих полей только после продуктового решения.
* **LLM** — provider, API key, model; backlog selector как «Advanced» внутри LLM.
* **Character** — gaze, passive companion.
* **Avatar** — VRM selection, normal preview entry, idle/animation только если эти пользовательские настройки подтверждены.
* **Overlay** — запуск, кадрирование, размер, прозрачность, click-through.
* **Advanced** — diagnostics, cache/reset; destructive history отдельно в Danger zone.

Сохранить текущую схему persisted config: меняются только представление и группировка. Проверка подключения должна стоять рядом с URL/provider, а не в общей footer. Save — primary, Close — secondary; Clear history — отдельно, с подтверждением.

## 8. Visual System (инкрементально)

* Spacing scale: 4, 8, 12, 16, 24, 32 px; page padding 24 px, между группами 24 px.
* Cards: один мягкий surface, радиус 10–12 px, граница только для разделения интерактивных/статусных блоков; не обводить каждое поле.
* Типографика: page title 24/30 semibold, section title 16/22, body 14/20, supporting text 12/16. Каждый экран имеет title + краткий subtitle.
* Buttons: Accent — одно основное действие на экран; Secondary — навигация/настройка; Negative — только destructive. Иконка сопровождает действие, но не заменяет подпись без tooltip.
* Status: healthy тихий нейтрально-позитивный chip; warning/error контрастны и содержат текст. Popover перечисляет ASR, TTS, LLM, Listening, Overlay; Runtime Health даёт detail и retry.
* Loading: skeleton для карточек/списков, отдельный progress для VRM. Пустые состояния должны содержать одно объяснение и одно действие.

Предлагаемые тексты:

| Состояние | Текст и действие |
|---|---|
| Нет диалогов | «Начните разговор с Shio.» — фокус в поле ввода |
| Сервисы недоступны | «Не удалось подключиться к сервисам речи.» — «Открыть настройки речи» / «Повторить проверку» |
| Нет модели | «Аватар ещё не загружен. Выберите VRM, чтобы открыть предпросмотр.» — «Выбрать модель» |
| Preview закрыт | «Предпросмотр закрыт и не расходует ресурсы.» — «Открыть предпросмотр» |
| Нет микрофона | «Выберите микрофон для голосового ввода.» — «Выбрать микрофон» |
| LLM не настроен | «Подключите LLM-провайдера, чтобы Shio могла отвечать.» — «Настроить LLM» |
| Listening выключен | «Непрерывное прослушивание выключено.» — «Настроить» |
| Overlay закрыт | «Оверлей сейчас не показан.» — «Открыть оверлей» |
| Debug данных нет | «События появятся после запуска Runtime.» — без ложного error-state |

## 10. Risks and Guardrails

1. Lazy VRM может нарушить publish state для overlay. Митигировать контрактным smoke test: overlay открывается до и после Preview, получает новое состояние и mouth weights.
2. Отделение canvas от `Controller.attachCanvas()` затрагивает текущую инициализацию health, microphone и continuous listening. Их надо вынести в лёгкий app bootstrap, не перемещая Runtime ownership.
3. Группировка Settings может потерять persisted values. Сохранить ключи config без переименования и добавить migration/read-back test.
4. Sidebar может переполнить минимальное окно. Нужен breakpoint и fallback выше, а не горизонтальное сжатие.
5. Shell конфликтует с нынешним fixed/absolute layout. Вводить в отдельной фазе с visual regression на 1200×800 и narrow widths.
6. Debug нельзя удалять или ослаблять. Переносится только discoverability, не telemetry, Runtime Health и тестовые controls.

## Architecture Review

Сверился с `ARCHITECTURE.md`.

Разногласий нет. Рекомендация меняет только presentation/lifecycle main-window canvas и навигацию. Она не переносит ответственность между Runtime, не меняет Character State, Conversation Admission, Avatar Runtime или Overlay contract. Реализация lazy Preview потребует отдельного архитектурного review до кода, поскольку затронет lifecycle renderer и связь с Overlay Runtime.
