# Техническое задание: живость персонажа и логическое ядро Shio

Статус: ТЗ для реализации. Дата: 30 октября 2026 года.
Ветка: `experiment/shio-autonomous-living-v1`.
Редакция 2: учтены коммиты `7eabd19` и `94d3d52` ревью-сессии.

Цель — сделать Shio заметно живее на видео обычного Chat и в простое, а также
усилить логическое ядро без расширения списка LLM-провайдеров. Документ
ненормативный: он не определяет архитектурный смысл и не заменяет
`ARCHITECTURE.md`. Пункты, которые конфликтуют с действующими инвариантами,
вынесены в гейты (раздел 4). Без отдельной явной авторизации пользователя
они не реализуются.

## 2 Обязательный результат

Результат оценивается по видимому поведению, а не по техническим PASS-гейтам.
Метрики измеряются на коротких клипах (30–60 с) обычного Chat с реальными
Character LLM, Fish и MotionBricks. Каждая метрика снимается до и после изменения.

| № | Метрика | Baseline | Цель |
|---|---|---|---|
| M1 | Доля речи с поднятой кистью (`gesture-coverage.cjs`) | 99,5% | ≥ 95%, без регрессии |
| M2 | Разница медианной высоты кисти: happy против sad | не измерялась | ≥ 5 см |
| M3 | Разница темпа битов: energetic против calm | не измерялась | ≥ 20% |
| M4 | Доля концов битов в ±120 мс от акцента речи | не измерялась | ≥ 60% |
| M5 | `speech_started` пользователя → первая видимая реакция (уши/взгляд), p95 | не измерялась | ≤ 150 мс |
| M6 | Доля паузы «думания» (`speech_ended`/`text_submitted` → `playback_started`) с видимым thinking-поведением | не измерялась | ≥ 90% |
| M7 | Самый долгий интервал простоя без видимого действия (кроме дыхания и моргания), нейтральное настроение | десятки секунд | ≤ 30 с |
| M8 | Знак `mood.valence` в сценарии «похвала» против «подкол» | не различается | различается |
| M9 | Медиана `text_submitted` → `playback_started` на direct-answer ходах | замерить | −30% (WI-13) |
| M10 | Протокольная корректность модели (Character eval) | замерить | без регрессии > 5% |
| M11 | p99 ускорения кисти во время речи | 3,29 м/с² | не выше +10% |
| M12 | CPU композиции кадра p95 | 2,0 мс | не выше +0,3 мс |

Целевые значения уточняются после WI-0. Ни одна метрика не засчитывается
синтетическим fixture вместо живого клипа.

## 3 Архитектурные границы

Перед каждым Work Item исполнитель читает `AGENTS.md` и релевантные разделы
`ARCHITECTURE.md` (20, 21E, 21F, 21G, 15). В отчёте каждого WI он перечисляет
применённые инварианты. Обязательные границы:

- **Avatar Runtime** — единственный владелец костей и model application.
  AvatarExpressionMixer — единственный финальный facial writer.
  Behavior, Alive и LLM никогда не пишут кости, morph weights, gaze или visemes.
- **Часы речи.** Разговорная моторика тактуется только фактически потреблённым PCM
  из AudioPlayer. Время прихода текста, ACK и счётчик кадров его не заменяют.
- **Overlay** только потребляет готовые projections и не запускает второй
  генератор тела, лица или головы.
- **MotionBricks** — единственный generated-body Adapter.
  Запросы к воркеру строго валидируются с обеих сторон, все поля ограничены.
  Сырые позы не попадают в diagnostics, Character State, историю или renderer state.
- **Mood** модулирует только bounded пороги, интенсивность воплощения, banter
  и cooldowns. Mood не генерирует текст и не даёт полномочий.
- **Experience Policy** остаётся детерминированным источником базовой оценки.
  Модельная поправка допустима только как bounded modifier, не как замена.
- **Нет роутинга по ключевым словам.** Никаких phrase-, keyword-, regex- или
  locale-маршрутизаторов для решений по естественному языку. Семантику решает
  Character LLM.
- **Conversation Admission** — единственный вход в Conversation Runtime.
  Автономная речь проходит Proactive Initiative Gate.
- **World Context** — только present-state метаданные. Никакой истории
  клавиатуры, буфера обмена, браузера и экрана.
- **LlmGateway и credential store** принадлежат Main. Renderer видит только
  наличие и источник ключа. Fast Brain принимает только строгий JSON
  и всегда получает cancellation.
- **Character Request Composer** ограничен по размеру и резервирует минимум
  для каждой присутствующей секции.
- **IPC.** Каждый новый endpoint проверяет sender и payload в runtime
  и есть в canonical channel inventory.
- **UI.** Новый UI делается на React Spectrum 2, поддерживает light и dark,
  все строки есть на RU и EN.

## 5 Инженерные принципы

Принципы обязательны для каждого WI и проверяются в ревью.

**Single Responsibility.**
- Новая логика живёт в новых маленьких модулях с одной ответственностью.
- В крупные файлы добавляется только wiring, без новой бизнес-логики:
  `CharacterToolLoop.ts` (1,6 тыс. строк после `94d3d52`),
  `GeneratedBodyPlayback.ts` (2,5 тыс.), `GeneratedBodySafety.ts` (1,4 тыс.),
  `AvatarController.ts` (1,2 тыс.).
- Planning-логика уже вынесена в `CharacterToolRequirementPlanning.ts`.
  Новые поля планирования добавляются туда, а не в `CharacterToolLoop.ts`.
  Та же схема для протокола (`CharacterToolProtocol.ts`), evidence
  (`CharacterToolEvidence.ts`) и контекста результатов (`CharacterToolResultContext.ts`).
- Политики (стиль, idle, backchannel, appraisal, resolver ролей) — чистые
  функции или классы без side effects. Side effects остаются у владельцев.

**Open/Closed.**
- Расширяемые наборы задаются данными и registry, а не новыми `if`:
  idle-активности, отображение стиля подачи, keyposes жестов, проверки eval,
  уровни протокола.
- Новая активность или проверка добавляется записью данных и, при
  необходимости, одной стратегией.

**Liskov.**
- `LlmGateway.forRole()` и failover-декоратор возвращают тот же `LLMProvider`.
  Потребители (Tool Loop, Fast Brain, Browser vision, backlog selector)
  не меняют код вызова.

**Interface Segregation.**
- Узкие порты: `MotionAttenuationProbe`, `DeliveryStyleSource`,
  `UserSpeechActivitySource`, `IdleActivitySink`.
- Не передавать `Controller`, `AvatarController` или весь `AliveFacade` туда,
  где нужен один метод.

**Dependency Inversion.**
- Политики получают clock и seeded RNG через параметры.
- Внутри политик запрещены `Date.now()` и `Math.random()`. Детерминизм
  достигается в тестах через `tests/support`.

**DRY и единый источник правды.**
- **Канонические контракты** лежат в `contracts/`. TS и Python артефакты
  генерируются sync-скриптами с режимом `--check`, по образцу
  `sync-emotions.mjs` и `sync-motion.mjs`.
- **Одни константы на TS и Python.** Числа не дублируются вручную между
  `targets.py` и renderer.
- **Общий helper подавления.** Условия «suspended / privacy / off / quiet hours /
  busy» сейчас дублируются в `BehaviorRuntime` и `AmbientPresencePolicy`.
  Их нужно вынести в один helper и переиспользовать в новых политиках.
- **Существующие runner'ы.** Квалификация расширяет `qualifications/llm/qualify.ts`
  и `qualifications/speech-motion/gesture-coverage.cjs`, а не копирует их.
- **Одна сборка запроса.** Direct-запрос к LLM строится в одном месте
  (WI-13), без копии сборки сообщений.
- **Один приём LLM-запроса.** Проверки ключа, streaming и vision живут только
  в `LlmGateway.prepare()` (после `7eabd19`). Роли и failover (WI-9)
  переиспользуют его, а не повторяют проверки.
- **Существующие хуки наблюдения.** Для телеметрии тела использовать имеющиеся
  `MotionFilterContext.onProjected`/`onIntegrated` и `MotionDynamicsObserver`
  в `GeneratedBodyPlayback`. На них уже опираются qualification runner'ы.
  Параллельный механизм хуков не создавать.

**KISS и YAGNI.**
- Наименьшее безопасное изменение. Никаких абстракций «на будущее»,
  новых Runtime и второго источника состояния.

**Разделение рефакторинга и поведения.**
- Извлечение без изменения поведения и изменение поведения — разные коммиты.
- Извлечение доказывается тестом эквивалентности выходов.

**Качество.**
- Biome и `tsc` без blanket-подавлений.
- У каждого таймера, подписки и listener есть идемпотентный teardown.
- У каждого detached Promise есть observer.

## 6 Тестовая стратегия

| Уровень | Где | Что |
|---|---|---|
| Unit | `apps/desktop/tests/unit/<domain>` | Чистые политики, resolvers, checkers, валидация схем |
| Contracts | `apps/desktop/tests/contracts` | Схемы контрактов, sync `--check`, wire-протокол motion |
| Architecture | `apps/desktop/tests/architecture` | Владение и границы импортов (см. ниже) |
| Integration | `apps/desktop/tests/integration/<domain>` | Взаимодействие владельцев с фейковыми LLM, clock и PCM |
| Python | `apps/desktop/motionbricks/test_*.py` | `targets.py`, `activity.py`, валидация и детерминизм |
| Qualification | `apps/desktop/qualifications/*` | Живые клипы, реальные провайдеры, eval; не входит в regression |

Обязательные правила:

- **Тест первым.** Для каждой новой политики сначала пишется unit-тест.
  Для бага сначала нужен воспроизводящий тест (RCA, `AGENTS.md` раздел 9).
- **Тесты описывают наблюдаемое поведение владельца.** Без исторических меток
  и нумерации в названиях.
- **Обязательные случаи:** границы значений, отказ валидации, cancellation,
  повторный teardown, Privacy/Suspend/Off, отсутствие optional capability.
- **Новые architecture guards:**
  1. Alive и Behavior не импортируют renderer avatar.
  2. Только Mixer пишет VRM expressions (проверить существующий guard и расширить).
  3. Только `LlmGateway` создаёт providers.
  4. Курсор и оценка хода не попадают в persisted stores, prompt и diagnostics
     сверх разрешённого.

### WI-1 Атрибуция ограничителей и профиль выразительности

**Цель.** Видеть, какой слой гасит движение, и держать художественные пределы
в одном месте.

**Требования.**

1. **Порт `MotionAttenuationProbe`.**
   - Сигнатура: `report(stage, channel, requested, applied)`.
   - В production по умолчанию no-op, без аллокаций в кадре.
   - Stage — enum:
     - тело: `standing-arm-range`, `recover-rest`, `body-safety.workspace`,
       `body-safety.contact`, `body-safety.hinge`, `adaptive-filter`;
     - голова: `head-authority`;
     - лицо: `expression-mixer`, `lipsync-clamp`.
   - Channel: `leftHand`, `rightHand`, `head`, `torso`, `mouth`, `brows`.

2. **`MotionAttenuationAggregator`.**
   - Скользящее окно 1 с, ограниченный ring buffer.
   - Отдаёт только безразмерные доли и счётчики. Без поз, координат и костей.

3. **Инструментирование.**
   - Подключить probe к перечисленным слоям через существующие `getDebugState()`.
     Новый канал diagnostics не создавать.
   - Для тела опираться на уже существующие `onProjected`/`onIntegrated`
     в `MotionFilterContext` и `MotionDynamicsObserver` (раздел 5, DRY).
   - Атрибуцию разделять по флагу `generatedSource` из `7eabd19`: генерируемое
     тело и локальная presence ограничиваются разными параметрами.
   - В `AdaptiveMotionFilter` отдельно учитывать потолок скорости presence
     (1,6), полосу трекинга генерируемой presence (8 против 28)
     и `MOTIONBRICKS_CONVERSATION_MAX_JOINT_SPEED`. Это кандидаты на скрытое
     гашение движения.

4. **Debug UI.** Секция в Debug Preview / Runtime diagnostics: топ-3 гасящих слоя
   по каналам. Spectrum 2 (`TableView`, `Meter`), RU/EN, light/dark.

5. **`renderer/avatar/tuning/expressivenessProfile.ts`.**
   - Собирает все художественные пределы:
     - `standingArmRange` и затухание после речи;
     - доля recover rest;
     - `facialTuning.lipSync.clamps`;
     - веса эмоций в `FacialProfile`;
     - потолки `headMotionTuning`;
     - амплитуды `MicroMotionController` и `PostureShiftController`.
   - Физические ограничения (контакты, шарниры, калибровка торса, скорости)
     в профиль **не** переносятся.

6. **Порядок коммитов.**
   - Коммит 1 — извлечение без изменения поведения.
   - Коммит 2 и далее — тюнинг по данным атрибуции.

**Тесты.**
- Aggregator: окно, границы, переполнение.
- No-op probe ничего не аллоцирует.
- Каждый инструментированный слой сообщает долю `1` без ограничения и `< 1`
  при ограничении: `standing-arm-range.test.ts`, `adaptive-motion-filter.test.ts`,
  lipsync, mixer.
- Эквивалентность после извлечения: golden-выходы до и после совпадают.
- Architecture guard: потребители читают пределы из `expressivenessProfile`.

**Приёмка.**
- На живом клипе панель показывает атрибуцию.
- M12 не ухудшается.
- Отчёт называет 3 главных ограничителя и решение по каждому.

### WI-2 Стиль подачи (Delivery Style)

**Цель.** Тело, голова, уши и хвост передают одно эмоциональное состояние.

**Требования.**

1. **Контракт `contracts/embodiment-style.v1.json`.**
   - Для каждой канонической эмоции задаётся
     `{openness, height, tempo, sharpness, asymmetry, lean}`.
     Значения ограничены (`0..1` или `-1..1`).
   - Плюс bounded коэффициенты модуляции от Mood.
   - Desktop-only. `emotions.v3.json` не меняется, чтобы не затрагивать
     генерируемый API manifest.

2. **Скрипт `scripts/sync-embodiment-style.mjs`.**
   - Проверяет, что каждый `id` из `emotions.v3.json` присутствует
     (или задан явный default).
   - Генерирует TS для renderer и JSON для `motionbricks`.
   - Режим `--check` подключить в `desktop:check`.

3. **Чистая функция `resolveDeliveryStyle(emotionId, intensity, mood?)`.**
   - Живёт в `shared/`.
   - Модуляция от Mood не больше ±0,15 по каждой оси.
   - Mood берётся из существующего `AliveSnapshot.mood`. Нового store нет.

4. **Транспорт.**
   - Стиль добавляется в bounded `activity` запроса к воркеру.
   - Строгая валидация с обеих сторон: `activity.py` и Main-валидация запроса
     в `GeneratedMotionService`. Лишние ключи и значения вне диапазона отклоняются.

5. **Время смены стиля.** Стиль меняется на звуковой границе сегмента
   (существующий путь delivery cue по consumed PCM).

6. **`targets.py`.**
   - Выбор формы бита взвешен стилем: `sharpness` → press, `openness` → open,
     `height` → lift.

### WI-8 Эмоциональная петля: оценка хода

**Цель.** Содержание разговора влияет на Mood, а через WI-2 — на подачу.

**Требования.**

4. **Применение в `ExperiencePolicy`.**
   - Оценка — bounded модификатор базовой оценки, умноженный на `confidence`,

- Поправка ограничена.
- Без поправки результат прежний.

     бюджет уходит секциям по существующим tiers. Минимум каждой
     присутствующей секции сохраняется.

4. **Safe incremental filter** продолжает содержать все маркеры на любом уровне.

**Тесты.**
- Байтовая эквивалентность.
- Матрица выбора уровня.
- Распределение бюджета по уровням с сохранением минимумов
  (`prompt-budget.test.ts`).
- Фильтр на всех уровнях.

**Приёмка.**
- WI-10: консистентность персонажа на сильных моделях не хуже baseline.
- Протокольная корректность слабых моделей на `compact` выше baseline.

### WI-12 Сжатие контекста сессии

**Цель.** Shio помнит начало длинного разговора в пределах сессии.

**Требования.**

1. **`ConversationContextWindow`** вместо обрезки
   `InMemoryStore.MAX_MESSAGES = 20`.
   - Хранит последние N ходов дословно и одно скользящее саммари
     (≤ 1200 символов).

2. **Построение саммари.**
   - Роль `sessionSummarizer` (WI-9), асинхронно после хода при переполнении.
   - Single-flight, отменяется на shutdown.
   - При сбое — честный fallback на прежнюю обрезку с логом.

3. **Вход саммаризатора.**
   - Только проза user/assistant, уже лежащая в истории.
   - Без failure-презентаций (`assistantTurnKind`) и без сырых tool payloads.

4. **Composer.** Новая секция `sessionSummary` с бюджетом, минимумом и tier.

5. **Хранение.** Только память процесса. Сохранение между рестартами — гейт G3.

**Тесты.**
- Окно сохраняет последние N ходов.
- Саммари запускается при переполнении и не запускается дважды.
- Fallback при сбое.
- Исключение failure-ходов.
- Граница бюджета.
- Cancellation.
- Architecture guard: нет записи в SQLite и файлы.

**Приёмка.** Eval-кейс на 25 ходов: деталь из хода 2 используется на ходе 22.

### WI-13 Спекулятивный прямой ответ

**Цель.** Сократить паузу до голоса на ходах без инструментов.

**Требования.**

1. **Запуск.** При включённой настройке (по умолчанию выключена до измерения)
   streaming-запрос direct-ответа стартует параллельно с planning.

2. **Буфер.**
   - Ограничен по символам и времени.
   - Ничего не уходит в чат, TTS и историю до решения плана.

3. **План = direct answer без `plannedTools`.** Буфер выпускается через тот же
   safe incremental filter в исходном порядке. Typed embodiment плана остаётся
   авторитетным.

4. **Иначе.**
   - Спекулятивный запрос прерывается через `AbortController`.
   - Ход продолжается текущим путём.
   - Ни один фрагмент не показывается.

5. **Одна сборка.** Direct-запрос собирается одной функцией для обоих путей.
   - Planning остаётся в `CharacterToolRequirementPlanning.ts`
     (`requirementConversationMessages`, `parseToolPlanningResult`).
   - Координация спекуляции — отдельный модуль рядом, например
     `CharacterSpeculativeReply.ts`. В `CharacterToolLoop.ts` добавляется
     только wiring.

6. **Учёт.** Спекулятивные токены и отмены учитываются в latency/cost telemetry.

**Тесты.** На fake LLM с deferred promises:
- direct-план выпускает буфер по порядку и раньше;
- tool-план прерывает спекуляцию без показа;
- отмена хода прерывает оба запроса;
- переполнение буфера приводит к отмене спекуляции и fallback;
- ошибка спекулятивного запроса — fallback без дублирования.

**Приёмка.** M9 выполнен. Задержка ходов с инструментами не ухудшилась.

### WI-14 Партитура жестов по сегментам (гейт G1)

Начинается только после решения по G1. Предварительные требования к решению:

- **Протокол.** Каждый эмоциональный сегмент может нести ограниченный
  `gestureHint`, всего не больше 3 на ответ.
- **Исполнение.** На звуковом старте сегмента по consumed PCM, через
  существующую фазовую машину.
- **Отказы.** Действуют cooldowns, availability, protected stroke и expiry.
  Поздний жест истекает, а не догоняет речь.
- **Совместимость.** Typed visual decision из planning остаётся для первого
  сегмента.
- **Тесты.**
  - Инкрементальный фильтр на любых границах chunk.
  - Планирование по PCM-смещению сегмента.
  - Отсутствие повтора истёкшего акцента.
  - Prompt-budget.

## 9 Проверки

Во время работы запускаются точечные проверки. Перед каждым коммитом
выполняется полный набор для затронутого приложения (`AGENTS.md`, раздел 7):

```text
npm run desktop:check
npm run desktop:format:check
npm run desktop:imports:check
npm run typecheck
npm run desktop:test:fast
npm run desktop:test:regression
npm run build
```

Для изменений `motionbricks`: Python-тесты воркера (`test_*.py`) и Ruff
check/format, как в предыдущих motion WI. Изменения Main, preload и subprocess
требуют live Electron smoke. Новый root-скрипт eval: `desktop:qualify:character`
по образцу `desktop:qualify:llm`.

Живые клипы обязательны для приёмки WI-0–WI-7 и WI-13. Если запрос на live-проверку
не дан в задаче явно, исполнитель запрашивает его у пользователя перед запуском
(`AGENTS.md`, раздел 7). Непроведённая проверка прямо указывается в отчёте.

## 10 Definition of Done

Каждый WI:

1. Статические проверки, typecheck, fast и regression, build — PASS.
2. Новые и изменённые политики покрыты unit-тестами, включая границы,
   cancellation и teardown.
3. Новые строки UI есть на RU и EN. UI на Spectrum 2, проверен в light и dark.
4. Метрики раздела 2 сняты до и после на живых клипах, где это применимо.
   Ухудшения и неудачи указаны честно.
5. Отчёт в `docs/` в формате раздела 13 `AGENTS.md` с Architecture Review.
6. `ARCHITECTURE.md` и `AGENTS.md` не изменены без отдельной авторизации.
7. Отдельный коммит. Рефакторинг и поведение не смешаны. Push только по запросу.
